# Pixel Artist

Use the connected Pixelator MCP tools. Pixelator stores and draws pixels; you make the artistic decisions. It contains no model or agent runner. Discover the available tool schemas rather than guessing arguments. If the service is unavailable, report the connection problem; do not substitute an unrelated image generator.

Before every artist task, call `get_workflow` and apply its current `artistGuide` throughout drawing and review. The same guide is available as `pixelator://artist-guide` and in [references/artist-guide.md](references/artist-guide.md). It covers silhouettes, clusters, palette/value control, lighting, edges and game readability, with primary-source links. The service supplies it again when starting or resuming a run, including when a locally installed copy of this skill is older.

## Create and improve

1. Read the project and its style with `list_projects`. Reuse a suitable project or create one. Resolve size, palette, perspective and lighting from the request and project; make small artistic decisions without repeated questions. Canvas width and height accept positive integers without a fixed resolution cap, subject to available memory and runtime limits. Front/side views are supported. An asset keeps the color budget it is created with (presets allow 16 colors or fewer, at most 32): set `maxColors` in `create_asset` when it may need more, or raise it later with the `palette` operation's `maxColors`.
2. For a reference or variant, load the source with `get_asset` and **inspect its actual image**. Preserve its palette, proportions, lighting and important equipment. Use `create_variant` when continuing an existing asset family; reference metadata alone does not establish visual consistency. Bring existing pixel art in with `import_png`, preferably from a local `path`.
3. Open an artist run with `start_run`, attaching the existing asset when editing or continuing a variant. For a new sprite, plan the silhouette, body and equipment, then create the canvas with `create_asset` and its `runId`. Use named semantic layers such as `body`, `armor` and `sword` so later edits remain local. Give assets names and tags that `find_assets` will find; `update_asset` corrects them. After a restart or in a new session, find unfinished runs with `list_runs` and continue them with `resume_run`.
4. Construct the sprite with bounded `apply_operations` batches: shapes and lines for the silhouette and forms, followed by outline, shade and a few readable details. Each operation uses `op`, not `type`; for example `{ "op": "rect", "layerId": "body", "x": 10, "y": 8, "width": 6, "height": 9, "color": 2, "filled": true }`. Pixel indices refer to the document palette; index `0` is transparent. Reuse palette entries. Erase with index `0`. For hand-placed blocks prefer the compact `rows` operation over `patch`: one string per row, `.` transparent, `1`-`9` and `a`-`w` for palette indices 1-32, for example `{ "op": "rows", "layerId": "body", "x": 12, "y": 4, "rows": [".11.", "1221", ".11."] }`; `"mode": "over"` keeps existing pixels under `.`. The compact response returns the new `revisionId` for the next batch; request `response: "full"` only when you need the whole summary. Do not generate a normal illustration and downsample it, use imagegen as a substitute, or execute drawing scripts outside the engine.
5. After a meaningful drawing stage, call `inspect_asset` with the current asset, revision and `runId`. It returns a real PNG as MCP image content. Pass `scales: [1, n]` to receive the native image for game readability and an enlarged image for pixel cleanup in one call; choose `n` so the enlarged image stays around 1024 px (16 for 32 px sprites, 8 for 64–128 px), because clients downscale larger images and blur the pixel grid. Pass `background` with the intended game background color: clients show bare transparency as white or black, which hides light or dark edges. When the background is unknown, check once on a dark and once on a light color. **Look at those images**. Once the first complete drawing is ready, call `record_review` for exactly that revision using the Artist Guide's review checklist, concrete observations and issues. Intermediate inspections need not consume the limited review budget. Do not infer the appearance solely from operations or validation JSON. If the client cannot deliver the image to you, report that limitation and finish as `needs_review` instead of claiming visual inspection.
6. Fix specific observed issues, inspect the new image and record another review. Allow at most three correction rounds after the first complete drawing. Respect the run's server limits and aim for ordinary tasks to finish within ten minutes. Stop sooner when improvements stall; retain the best valid result and name unresolved issues.
7. Call `validate_asset` and ensure the current final revision has been inspected and reviewed. Reuse its existing final review when no further edit occurred; do not spend another review merely to finish. Call `finish_run`: use `completed` when the requested work is done and technical checks pass; otherwise use `needs_review`. Return asset/revision IDs, a brief account of changes and any remaining limitation. Export with `export_asset` when requested: `outputDir` writes stable file names straight into the game folder, and for Unity pass the same `pixelsPerUnit` (usually the tile size) for every asset.

## Animate

Animations are frames of one asset that share its semantic layers, palette and pivot. Create them with `create_asset` and `frames` (for example `[{ "id": "walk_1", "durationMs": 120 }, ...]`) and optional `animationTags`, or add frames to an existing asset with frame operations.

1. Draw the first key pose completely and inspect it.
2. Build further frames from it instead of redrawing: `duplicate_frame` (copy directly after the source), then change only what moves with `stamp` (copy a region from any frame/layer with `dx`/`dy`; `mode: "over"` keeps pixels under transparent source pixels), `move` and `rows`. Every drawing operation targets one frame: set `frameId` or a single `editScope.frameIds` entry; `editScope.frameIds` protects all other frames.
3. Frame structure and timing (`add_frame`, `duplicate_frame`, `remove_frame`, `reorder_frames`, `frame_duration`, `set_tags`) needs every layer in `editScope.layerIds`, no `rect` and `allowFrameChanges: true`. Tags are zero-based and inclusive and follow inserted or removed frames.
4. Inspect the whole animation as one sprite sheet: `inspect_asset` with `runId` shows all frames in timeline order (or `tag`/`frameIds`), separated by a gutter color outside the palette; add `onion: { "before": 1 }` to see the previous frame tinted blue behind each frame. Review the Artist Guide's Motion point. Finishing as `completed` requires an inspection that showed every frame.
5. Export with `export_asset` `format: "sheet"` (PNG plus Aseprite-compatible JSON with durations and tags) or `format: "unity"` (one sprite per frame and one clip per tag).

## Tiles

Tilesets are assets with a tile grid (`create_asset` with type `tileset`, `tileWidth`/`tileHeight` and a canvas that is a multiple of them). Tile IDs count row by row; frames animate every tile together.

1. For autotiles draw only the key tiles in the first template row: single, horizontal, vertical, cross (four sides with inner corners) and fill; the edge template needs the first four. Then apply `autotile` with `template` `blob` (47 tiles, mixed terrain), `edge` (16) or `corner` (keys plus 15) and optional `x`/`y` (template origin in tiles). It composes every other tile from quarters of the keys and labels them with Tiled/Godot terrain. Use even tile sizes.
2. Check seams with `inspect_asset` `preview: "wrap"` (3×3 repetition) for seamless textures, `preview: "tiles"` to judge each tile, and `preview: "terrain"` for a sample map painted by terrain matching; magenta cells and `missingCells` mean missing combinations. Fix key tiles and run `autotile` again rather than editing generated tiles by hand. `shift` with half the tile size moves edges into the middle for cleanup.
3. Set names, `type`, `probability`, `collision` rectangles and terrain labels with `tile_properties`; terrain uses Tiled's Wang order (top, top-right, right, bottom-right, bottom, bottom-left, left, top-left) plus the center.
4. Export with `export_asset` `format: "tiled"` (PNG, .tsj, .tsx), `"godot"` (PNG, .tres) or `"unity"`; `extrude: 1` prevents texture bleeding. Level design itself stays in Tiled or the engine.

## Precise editing

- Read the current document and revision before changing an existing asset. Identify the target layer and source/destination bounds; do not redraw the entire character for a local request. Use `read_pixels` with a `rect` (and `layerId` when needed) to get the exact indices of the region in the same row encoding, edit those rows and write them back with `rows`; reserve `get_asset` `includePixels` for whole-document needs.
- Supply `expectedRevision`, a unique `requestId`, `actor: "agent"` and the active `runId` on each operation batch. Retry a lost response with the **same** request ID and payload. On a revision conflict, reload and reassess the edit rather than overwriting newer work.
- Set `editScope.layerIds` and, for a local edit, `editScope.rect` to the smallest region covering the intended change. Include both old and new bounds when moving a part. Keep palette and layer structure changes disabled unless the task needs them. Palette replacement can affect the whole sprite.
- For an irregular region, add `editScope.mask` (one string per `rect` row, `#` writable, `.` protected); fill, replace and outline then stay inside it. `outline` takes `corners: false` for a four-neighbor outline and `reference: "composite"` to outline all visible layers onto a separate layer.
- Preserve locked layers and everything outside the permitted scope. Inspect the result and its diff, then verify that the requested pixel-distance or color change actually happened. If the canvas prevents the edit, explain the constraint rather than silently resizing or clipping; use `resize_canvas` (full scope, `allowLayerChanges`, `offsetX`/`offsetY` place the old content) only when the user asks for a different canvas size. `merge_layers` destroys semantic layers, so merge only on request.
- Reuse stored revisions for comparison or recovery. `restore_revision` creates a new current revision; inspect that new revision before finalizing it.

Technical validity is measurable; silhouette readability, style, lighting and identity require visual judgment. Reviews and scores are observations, not proof of art quality. Tile maps (level layouts) and asset-pack orchestration are not part of Pixelator; do not claim those exports exist.

Judge small assets at their native size as well as enlarged. Reserve contrasting pixels for the features that explain the object: a character's face and equipment, or a bottle's neck and stopper. A correct outline and palette do not make a featureless shape game-readable.
