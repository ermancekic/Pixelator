# Pixelorama shows which drawing aids improve Pixelator

Pixelorama is particularly strong at supporting typical pixel art tasks directly on the image: drawing clean lines, building shapes symmetrically, using outlines on other layers for filling, and judging results independently of the working zoom. **For Pixelator we therefore adopt four related improvements: drawing symmetry with an optional pixel-perfect pencil, more flexible filling, a reliable preview and atomic layer duplicates.** The selection strengthens both manual editing and the data state shared with MCP. It requires no new animation or tilemap structure. Preview, layer ordering, palettes and revisions already exist; the improvements close specific gaps in them. The selection is based on the official repository, official documentation sources and the local code, researched on 17 October 2026.

## Pixelorama combines drawing aids with direct image control

Pixelorama's feature set ranges from pixel-accurate lines and indexed color to animation, tilemaps and non-destructive effects. What convinces us for Pixelator is above all the working principle: a frequently needed action gets a suitable option right in the drawing flow. The official overview lists, among other things, pixel-perfect lines, palettes, Tile Mode and layer effects. Which of these we choose is a product decision for Pixelator's current scope, not a claim about measured productivity gains. ([Pixelorama feature overview](https://github.com/Orama-Interactive/Pixelorama#features))

Pixelator does not start from zero. Zoom to the mouse pointer, panning, actual size, grids, keyboard shortcut help, visible and locked layers, ordering, flipping, rotation and a small preview already exist. There are also index-based palettes, revisions and shared browser/MCP editing. Introducing these again would be unnecessary. **The biggest gain lies where existing foundations do not yet fully support a step:** for example a preview labeled “1:1” that shrinks large images because of CSS maximum sizes, or a bucket fill that cannot yet take an outline on another layer into account. ([Local editor](../web/App.tsx), [Existing controls](../docs/editor.md))

## Symmetry and pixel-perfect improve the stroke itself

For each drawn point, Pixelorama computes horizontal, vertical and combined mirror points. Its implementation also supports diagonal and project-specific symmetry axes. For Pixelator we choose a deliberately simple variant: left/right and top/bottom around the canvas center. This makes it possible to lay out front-facing faces, shields, doors and UI icons symmetrically right away. Pencil, eraser, line and shapes use the same options; selection and move keep their own meaning. ([Pixelorama: mirror points](https://github.com/Orama-Interactive/Pixelorama/blob/master/src/Autoload/Tools.gd#L607-L650))

The optional **pixel-perfect mode removes redundant right-angle corner pixels from a 1-pixel pencil stroke**. Pixelorama enables its equivalent handling at brush size one. The drawer detects local L-shaped bends and restores the original color at the removed intermediate point. This distinction is crucial: removing a corner pixel must not erase existing artwork underneath. ([Pixelorama: activation](https://github.com/Orama-Interactive/Pixelorama/blob/master/src/Tools/BaseDraw.gd#L388-L405), [Pixelorama: PixelPerfectDrawer](https://github.com/Orama-Interactive/Pixelorama/blob/master/src/Classes/Drawers.gd#L34-L54))

The chosen implementation builds both aids on Pixelator's existing stroke preview and pixel operations. Pixel-perfect first processes the ordered source path; the mirror points are created afterwards. Every target point is clipped to the selection, and center points are not written more than once. The original and its counterparts form one stroke and one revision. The normal pencil remains available, because a deliberately jagged path can be just as correct. ([Code mapping: drawing helpers](../web/drawing-helpers.ts), [Editor integration](../web/App.tsx))

## The bucket fill separates image reference and edited layer

Pixelorama's bucket distinguishes contiguous areas from all pixels of the same color and can sample merged visible layers. The reference determines which pixels belong to the area; writing still goes to the target cels. This supports a common workflow: outlines sit on top, and a separate color layer below should be filled within those outlines. ([Pixelorama: bucket modes and reference](https://github.com/Orama-Interactive/Pixelorama/blob/master/src/Tools/DesignTools/Bucket.gd))

For this, Pixelator gets two independent choices: **contiguous or same color**, and **active layer or visible composite as the reference**. The previous combination remains the default. The engine uses exact palette indices and four neighboring pixels for contiguous areas. Hidden layers do not affect the composite reference. An allowed edit scope still limits the writable area; other layers are only read when needed. ([Code mapping: operation types](../src/types.ts), [Raster engine](../src/engine.ts))

This delivers more than another global color swap, which the engine already handles via `replace`. Only the combination of composite reference and separate target layer makes targeted coloring beneath an existing outline possible. At the same time, existing MCP commands stay understandable thanks to optional parameters and unchanged defaults. Color tolerance, soft transitions and pattern libraries are not needed for the current exact index raster.

## An honest preview shows readability and tile seams

Pixelorama has its own preview camera with a zoom slider. This lets you judge the whole image while the main view stays on a detail. The principle fits Pixelator's artist workflow especially well: outlines are edited zoomed in, while readability has to work at actual size at the same time. ([Pixelorama: preview zoom](https://github.com/Orama-Interactive/Pixelorama/blob/master/src/UI/CanvasPreviewContainer/CanvasPreviewContainer.gd))

The chosen preview shows **1×, 2×, 4× or 8× without automatic downscaling**. Large views scroll. Checkered, light and dark backgrounds help to judge transparency and low-contrast edges. This background choice is our own derived improvement; the research does not claim a specific current Pixelorama menu feature for it. The existing current document state ensures that strokes in progress and viewed revisions appear in the same preview. ([Code mapping: AssetPreview](../web/AssetPreview.tsx), [Styling](../web/styles.css))

In addition, a 3×3 view repeats the same asset on all edges. Pixelorama's Tile Mode is the inspiration; Pixelator's implementation is initially a pure tile preview. It reveals visible seams without enlarging the asset or creating a new revision. A tileset with multiple tiles, neighbor rules and map editing remains a separate feature. ([Pixelorama: canvas options](https://github.com/Orama-Interactive/Pixelorama#features))

## Layer duplicates preserve variants without a new document model

Pixelorama clones a layer with its content, inserts the copy above the source and records the step in undo/redo. For Pixelator we choose `duplicate_layer` as an atomic engine operation, available in the browser and through the existing MCP editing. A copy gets a new ID, its own pixel buffer, and the source's visibility and lock state. This makes it possible to vary equipment or shading while the original stays unchanged. The existing rules for structural changes and layer limits continue to apply. ([Pixelorama: CloneLayer](https://github.com/Orama-Interactive/Pixelorama/blob/master/src/UI/Timeline/AnimationTimeline.gd), [Code mapping: engine](../src/engine.ts), [Operation contract](../src/contracts.ts))

Animation with a timeline, onion skinning and frame tags is another major Pixelorama strength. However, it does not fit into a small addition to today's single-image document: frames, timing and export relationships require an extended document model. The same applies to full tilemaps and extensive layer effects. This work gets its own planning as soon as it becomes a concrete product goal. ([Pixelorama: animation and tilemaps](https://pixelorama.org/))

The chosen concepts are implemented independently in TypeScript. No Godot code, shaders or graphics are copied; Pixelorama's MIT license is documented as the origin of the studied software. The research justifies the selection and describes how it maps to the code. **It does not confirm any executed tests**; technical expectations are in the acceptance matrix, actual results belong in the verification report. That keeps the next decision clear: first verify these complete drawing workflows, then decide based on concrete user tasks which larger extension is worth its effort.
